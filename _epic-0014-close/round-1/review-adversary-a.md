### Findings

**MINOR — `check_level_confinement` misses levels confined to an excluded third group value in multi-valued `group` columns**
File: `oaxaca_blinder/src/builder.rs:161-212` (the check itself), interacts with `builder.rs:477-488` (`prepare_data`'s dummy-column fallback).
Failure scenario: `self.group` has 3+ distinct values (e.g. `{"F","M","X"}`), and the comparison is `reference_group="F"` vs the other alphabetically-first non-reference value, `"M"` (per `split_groups`, `builder.rs:103-144`). A `categorical_predictors` level that appears **only** in `"X"`-group rows is absent from both `df_a` and `df_b`. `check_level_confinement`'s `full_levels` is built strictly as the union of `levels_in_a ∪ levels_in_b` (`builder.rs:180-185`), so a level absent from *both* never enters the scan — it's a silent no-op for this shape. But `create_dummies_manual` builds its one-hot columns from the **full, unsplit** `df` (all 3 group values) before the split (`run()`: `builder.rs:1037-1049` runs before `split_groups` at `1057`), so that level still gets a dummy column, which is then all-zero within both `df_a`'s and `df_b`'s own per-group matrices (`prepare_data`, `builder.rs:477-488`: the column exists by name, just constant-zero on values). An all-zero column makes `X'X` singular exactly as today (`math/ols.rs:100-105`) — this is a real, pre-existing failure case that the new named refusal was supposed to close but doesn't reach; it silently falls through to the old opaque Cholesky message.
Fix: scan `full_levels` from the levels present in the **unsplit** `df` column (or explicitly union in the excluded-group levels) rather than only `levels_in_a ∪ levels_in_b`, so a level absent from the compared pair for *any* reason gets the named refusal.

**MINOR — weighted requests bypass the check via zero-weight rows**
File: `oaxaca_blinder/src/builder.rs:161-212` (no `self.weights_col` awareness) vs. `oaxaca_blinder/src/math/ols.rs:51-79` (weighted Gram matrix `X'WX`).
Failure scenario: a categorical level has nonzero row count in group A but every one of those rows has `weight == 0`. `check_level_confinement` only checks non-null string *presence* in the raw column (`.into_iter().flatten()`, ignoring weights entirely) — the level "passes" pre-flight. But in `ols()`'s weighted branch, `x_w` is scaled by `sqrt(weight)` row-wise before `X'WX` is formed (`ols.rs:65-73`), so a level whose rows are all zero-weight contributes an effectively-zero column to `X'WX` in that group — the same singularity Cholesky already rejects, still unreached by the new named error. Narrow (only affects `weights()`-using callers), and correctly out of AC-1's literal example set, but it's the same defect class silently surviving.
Fix: when `self.weights_col` is set, treat a level as present only if its total weight in the group is `> 0` (sum weight per level, not just non-null count), or explicitly document the gap.

**MINOR / informational — local dev footgun in D3's harness, not a logic bug**
File: `verification/browser-parity/package.json:8` (`pretest` script) vs. the CI job's dedicated step (`ci.yml:207-208`).
`npm run pretest` only fires automatically through `npm test`; a developer invoking `npx playwright test` directly bypasses it. If `native-baseline.json` is missing, this hard-fails (`readFileSync` ENOENT) — fine, loud. But if a **stale** `native-baseline.json` lingers on disk from a prior `npm test` run (gitignored, not auto-cleaned) and the fixture/engine changes since, a direct `npx playwright test` invocation would silently compare against stale data rather than the current native build. Not a defect in `native-wasm-diff.mjs`'s comparison logic (verified clean below) — just a gap between the documented entry point (`npm test`) and what a shortcut invocation does. No fix required unless you want to guard it (e.g., `pretest` could `rm -f` the stale file first, or the spec's stated harness entry point is the only supported one and this is accepted).

### Hunt items — clean

1. **Behavior change for data that estimates today (AC-1 regression hunt):** No false positives found. Constructed and traced the sharpest candidates:
   - *Numeric-coded categoricals* — not a new failure. `create_dummies_manual` (`builder.rs:524-562`) already requires `.str()?` to succeed on the same column, and runs **before** `check_level_confinement` in both `run()` (`1037-1049` before `1060`) and `decompose_quantile()` (`880-892` before `899`). A non-string categorical column already hard-fails upstream today; the new check never sees it.
   - *Levels absent from BOTH groups* (2-group case) — genuinely a no-op for the check (union-based scan), but also structurally harmless: such a level never gets a dummy column materialize with nonzero values in either group's design matrix, so there's nothing for Cholesky to reject either. (This is the *3-group* variant, above, that's the real gap — not the plain 2-group case.)
   - *NaN/null levels* — `clean_dataframe` (`builder.rs:1003-1027`) already drops null rows in every `categorical_predictors` column before either `run()` or `decompose_quantile()` reaches the new check, so `.flatten()`'s null-filtering is a no-op against already-clean data, not new behavior.
   - *Reference-category-absent-from-a-group* (the subtler collinearity shape, dummy-sum ≡ intercept) — correctly caught: the scan considers **all** raw levels including the reference (nothing is excluded pre-dummy-encoding), matching the doc comment's own claim (`builder.rs:146-155`).
   - Confirmed structurally that `β_a`/`β_b` are **always** separate per-group OLS fits regardless of `reference_coeffs` (`estimation.rs:53-54`) — Pooled/Neumark only reweight a *later* `beta_star`, so the check's "does this raw level appear in df_a's own rows / df_b's own rows" condition is the exact trigger condition for both estimators' Cholesky calls (OLS and Heckman both consume the same `x_a`/`x_b` from `prepare_data`).

Outer loop is over `self.categorical_predictors: Vec<String>` (user's declared order), matching the spec's "column order then level sort." The function is plain sequential code — no `into_par_iter`, no dependency on `rayon::current_num_threads()` — called once on the un-resampled full group split, so it's thread-count-invariant by construction, not by luck.
